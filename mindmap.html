The Closer — Inbound BDR Hackathon

Thought Process — Inbound BDR Agent Pipeline

How the problem was broken down: delegated across 7 scoped, independently-callable stages (6 required by the brief + 1 bonus), not one prompt doing everything. Solid cream boxes are pure logic (deterministic, always inspectable). Dashed boxes are live network fetches. Red is a real branch/decision point — what the system does when data is missing or ambiguous, not just the happy path. Green is the bonus stage.

Input
IN

Raw inbound email

The fixed brief input — name, title, company, subject, body. Only input to the whole system.

Qualification

Matching & decision point
4

Case Study Matching

Scores every fetched case study against terms derived from the email — company name AND any referenced company, not just the one named in the email.

stages/stage4_case_study.py

→
?

Existing-account check

If the top match is the lead's own company (not just the referral), this is flagged as a likely expansion signal, not a cold lead — changes Stage 2 positioning and Stage 5's partner logic downstream.

Research synthesis & drafting
2

Deep Account Research

Synthesizes F1–F3 + the Stage 4 signal. Anything not found is marked UNVERIFIED, never guessed.

stages/stage2_research.py

→
3

Response Generation

3-email sequence assembled from Stage 1's gaps + Stage 2's findings. LLM-pluggable; falls back to structured template logic if no key is configured — never silently generic.

stages/stage3_response.py, llm_adapter.py

Routing & handoff
5

Partner Identification

If the matched case study is the lead's own existing site, prefer that site's real implementation partner (continuity) over a generic regional partner. Falls back to direct-AE if no partner signal exists at all — never invents one.

stages/stage5_partner.py

→
6

AE Handoff Summary

Pure synthesis of Stages 1–5 — introduces zero new claims. This is the "would an AE know what to do next" test.

stages/stage6_handoff.py

→
7

Impact Simulation (bonus)

Projects onto the 3 new sites using only metrics FlytBase already measured at this same customer's other site — labeled a projection, not a promise, with the 24/7-vs-daytime scale gap called out explicitly.

stages/stage7_simulation.py

deterministic logic (always runs, fully inspectable) live network fetch (degrades gracefully, never fabricates on failure) real decision/branch point bonus stage, beyond the brief's 6
Why delegated, not one big prompt: each stage takes typed input and returns typed output (see orchestrator.py), so any single stage can be tested, replaced, or audited without touching the others. The two decision points (existing-account check, partner continuity) are the parts of this system that couldn't be a static template — they only fire correctly because Stage 4 searches broadly instead of looking for one pre-known answer.
